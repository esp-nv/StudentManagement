Продължаване на разработката

Продължи работата по StudentManagement, като фокусът започна постепенно да се премества от основната CRUD функционалност към validation и по-добро разделяне на отговорностите.

Validation

Започна работа по validation на данните при създаване на Student.

Целта е неправилните данни да бъдат отхвърляни още преди да достигнат до database слоя.

Основният поток е:

User Input
    ↓
ViewModel
    ↓
Validation
    ↓
Controller / Service
    ↓
Database

CreateStudentViewModel

Започна по-ясното използване на ViewModel за входните данни при създаване на Student.

Това позволява да се разделят:

User Input


от:

Database Entity


По този начин entity моделът не е необходимо да съдържа всички правила и полета, които са нужни единствено на UI/application слоя.

Validation Rules

Започна добавяне на validation правила за Student.

Разглеждат се ограничения като:

задължителни полета;
допустима дължина на текстови полета;
валиден email формат;
допустима стойност за Age.

Validation трябва да бъде разбираема както за системата, така и за потребителя.

Validation Messages

Потребителят трябва да получава ясна информация защо въведената стойност не е приета.

Не трябва да се показват директно технически exception-и или database грешки като потребителски съобщения.

Разграничават се:

Validation Error


и:

Unexpected Exception

Separation of Concerns

Продължава да се оформя разделянето на отговорностите:

View
  ↓
ViewModel
  ↓
Controller
  ↓
Service
  ↓
Data Access
  ↓
Database


Всеки слой трябва да има ясна задача.

Service Layer

Продължава работата по Service layer, въведен като част от предходната архитектурна промяна.

Controller-ът не трябва постепенно да се превръща в място за:

validation logic;
business logic;
database logic;
обща application logic.
Clean Code

Започва да се обръща по-голямо внимание на:

малки и ясни методи;
ясни имена;
една отговорност;
избягване на дублиране;
избягване на ненужна сложност.
Database

Database остава SQL Server с Entity Framework Core.

Промените по модела трябва да бъдат извършвани чрез migration процес, за да може schema evolution да бъде проследявана.

Development Approach

    ↓
Next Change


Целта е всяка промяна да бъде контролируема и лесна за проследяване.
