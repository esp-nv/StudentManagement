# Historical Note – 2026-10-04

## CourseOffering

Днес продължихме с реализацията на CourseOffering като отделен domain entity между Course и Enrollment.

CourseOffering вече има собствен service layer чрез:

    `ICourseOfferingService
    CourseOfferingService
    `

Service-ът поддържа:

    `GetAllAsync
    GetByIdAsync
    CreateAsync
    UpdateAsync
    DeleteAsync
    `

При четене на CourseOffering се използва:

    `Include(co => co.Course)
    `

като стандартните queries филтрират soft-deleted записи.

CourseOffering вече проверява и дали свързаният Course е активен.

## CourseOffering ViewModel

Създаден е:

    `CourseOfferingViewModel
    `

който е предназначен конкретно за UI flow-а на CourseOffering.

ViewModel-ът съдържа:

    `CourseId
    StartDate
    EndDate
    EnrollmentStartDate
    EnrollmentEndDate
    Capacity
    Courses
    `

За dropdown selection е създаден отделен:

    `CourseSelectItemViewModel
    `

който съдържа:

    `Id
    Code
    Name
    `

Така UI не зависи директно от целия Course entity при избора на курс.

## CourseOffering Validation

Първоначално DateTime полетата бяха дефинирани като:

    `DateTime
    `

с `[Required]`.

При тестване на Create UI се установи важен проблем:

`DateTime` е value type и има default стойност `01.01.0001`, поради което `[Required]` не може да различи празно поле от реално подадена дата.

Полетата бяха променени на nullable:

    `DateTime?
    `

като `[Required]` остава върху тях.

Validation логиката в `IValidatableObject` беше направена null-safe чрез `HasValue`.

Това доведе до правилно UI поведение при празна форма:

    `The StartDate field is required.
    The EndDate field is required.
    The EnrollmentStartDate field is required.
    The EnrollmentEndDate field is required.
    `

Capacity използва `[Range(1, int.MaxValue)]` и правилно отхвърля `0`.

## CourseOffering Business Validation

Добавени са проверки за:

    `EndDate < StartDate
    EnrollmentEndDate < EnrollmentStartDate
    EnrollmentStartDate > StartDate
    `

При нарушение потребителят получава конкретна validation грешка и данните не се записват.

Проверено е, че същите правила работят и при Edit.

## CourseOffering UI

Реализиран е основният CRUD UI:

    `Index
    Details
    Create
    Edit
    Delete
    `

Create и Edit използват Course dropdown.

В dropdown-а се показва:

    `Code - Name
    `

Delete използва съществуващия soft-delete подход.

При CourseOffering Delete записът не се премахва физически от базата.

Вместо това:

    `IsDeleted = true
    `

След това стандартният CourseOffering list не го показва.

Това беше проверено както през UI, така и директно в базата.

## CourseOffering Testing

Направени са практически тестове през UI.

Проверено е:

    `Create
    Edit
    Delete
    Invalid dates
    Empty dates
    Empty Course selection
    Invalid Capacity

    `

При невалидни данни формата остава отворена и показва validation messages.

При валидни данни CourseOffering се записва успешно.

При soft delete записът остава в базата, но не се показва в стандартния списък.

## Enrollment Domain

След CourseOffering преминахме към Enrollment.

Потвърден е моделът:

    `Student
       ↓
    Enrollment
       ↓
    CourseOffering
       ↓
    Course
    `

Това означава, че Student не се записва директно в Course.

Enrollment е връзката между конкретен Student и конкретно CourseOffering.

Това позволява един Course да има множество различни провеждания и позволява запазване на историческите Enrollment записи.

## Enrollment Model

Потвърден е `Enrollment` model със:

    `Id
    StudentId
    CourseOfferingId
    EnrollmentDate
    Status
    IsDeleted
    Student
    CourseOffering
    `

Използва се `EnrollmentStatus` enum.

Статусите са:

    `Pending
    Active
    Cancelled
    Completed
    Failed
    NotAttended
    `

## Enrollment Service

Създадени са:

    `IEnrollmentService
    EnrollmentService
    `

Service-ът към момента поддържа:

    `GetByIdAsync
    CreatePendingAsync
    ApproveAsync
    `

При създаване на Enrollment:

- Student трябва да съществува и да не е soft-deleted.
- CourseOffering трябва да съществува и да не е soft-deleted.
- Не се допуска duplicate Enrollment за същия Student и CourseOffering.
- Новият Enrollment получава `Pending` status.
- `EnrollmentDate` се задава от application logic.
- `IsDeleted` започва като `false`.

## Enrollment Approval

Реализирана е базова логика за Approve.

Enrollment може да бъде одобрен само ако текущият му статус е:

    `Pending
    `

Преди активиране се проверява Capacity на CourseOffering.

Броят на текущите Active Enrollments се сравнява с Capacity.

Ако капацитетът е достигнат, Enrollment не се активира.

При успешно одобрение:

    `Status = Active
    `

## Enrollment ViewModel

Обсъдихме необходимостта от ViewModel за Enrollment.

На този етап не се добавят излишни полета в UI модела.

По-специално:

`EnrollmentDate` не трябва да се въвежда от Student.

`Status` не трябва да се избира от Student при първоначално записване.

Тези стойности са част от application/business logic.

Това предотвратява ситуация, при която UI потребителят може директно да зададе например `Active`.

## Student → Available Courses

За тестовия UI flow избрахме Student Details като естествена начална точка.

Идеята е в:

    `Students/Details
    `

под основната информация за Student да има секция:

    `Available Courses
    `

В горната част се показват на един ред:

    `First Name + Last Name
    Email
    `

След това се показва таблица с наличните CourseOfferings.

## Available Courses Rules

Първата версия на Student UI няма да бъде система за търсене и филтриране на всички курсове.

На този етап Student трябва да вижда само CourseOfferings, които са достъпни за записване.

Това означава:

- CourseOffering не е soft-deleted.
- Свързаният Course не е soft-deleted.
- Enrollment period е започнал.
- Enrollment period не е изтекъл.
- Student все още няма Enrollment за това CourseOffering.

По този начин Student вижда само реално достъпните в момента възможности за записване.

По-сложни функции за:

    `search
    filtering
    historical courses
    past offerings
    `

остават за бъдещ етап.

## Student Enrollment Actions

Първоначалният UI flow ще бъде минимален.

Основното действие е:

    `Enroll
    `

След създаване на Enrollment той започва като:

    `Pending
    `

За вече записан курс ще бъде предвидено действие:

    `Cancel
    `

Този подход ще бъде разширен по-късно, ако business requirements го изискват.

## Student Details UI

Потвърдихме, че `Students/Details` ще бъде използван първоначално и за тест на Enrollment функционалността.

Това позволява да тестваме реалния flow без да създаваме отделен сложен Enrollment dashboard.

Финалният дизайн на `Students/Details` ще бъде преработен по-късно.

На този етап приоритетът е:

    `Business logic
         ↓
    Service
         ↓
    Controller
         ↓
    Functional UI
         ↓
    Testing
         ↓
    Final UI design
    `

## Separation of Concerns

Продължихме да следваме установения принцип всеки слой да има конкретна отговорност.

    `Models
        ↓
    domain data

    ViewModels
        ↓
    UI-specific data

    Controllers
        ↓
    HTTP flow

    Services
        ↓
    business logic

    Views
        ↓
    presentation

    DbContext
        ↓
    persistence
    `

Enrollment business rules не се поставят само във View или Controller.

Особено важните проверки като Capacity, duplicate Enrollment и активност на Student/CourseOffering се изпълняват в Service layer.

## Validation и Security

При тестването на CourseOffering отново потвърдихме, че client-side validation не е достатъчна.

HTML ограниченията и browser validation са UX помощ.

Server-side validation и Service business rules остават задължителни.

Това е важно и за Enrollment.

Дори ако UI показва само допустими CourseOfferings, Service-ът трябва независимо да проверява дали операцията е допустима.

## Authorization

Authorization и Roles/Permissions все още не са имплементирани.

Enrollment flow-ът е структуриран така, че по-късно да може да бъде поставен зад authorization rules.

Не добавяме hard-coded role checks на този етап.

## Архитектурен принцип

Продължаваме с подхода:

    `Проблем
       ↓
    проверка
       ↓
    решение
       ↓
    implementation
       ↓
    UI testing
       ↓
    database verification
    `

При реален проблем първо се проверява причината, вместо да се добавя workaround само за да мине UI тестът.

Пример за това беше промяната от `DateTime` към `DateTime?`.

Тя не беше направена само заради компилацията, а защото реалното поведение на `[Required]` върху value type не отговаряше на желаната функционалност.

## Състояние в края на деня

Към края на работата:

    `Student CRUD UI е функционален;

    Course CRUD UI е функционален;

    Course използва soft delete;

    CourseOffering CRUD UI е функционален;

    CourseOffering използва soft delete;

    CourseOffering validation е функционална;

    Empty DateTime validation е коригирана чрез nullable DateTime;

    CourseOffering е тестван през UI и базата;

    Enrollment model е потвърден;

    EnrollmentStatus е създаден;

    IEnrollmentService е създаден;

    EnrollmentService е създаден;

    Pending Enrollment logic е реализирана;

    Enrollment approval logic е реализирана;

    Capacity проверката при Approve е реализирана;

    EnrollmentsController е създаден като базова структура;

    Student Details е определен като начална точка за Enrollment UI;

    Available Courses flow е дефиниран;

    Enrollment ViewModel ще бъде добавен според конкретния UI flow;

    финалният дизайн на Student Details остава за по-късен етап;

    search/filter функционалността за курсове остава за бъдещ етап;

    Roles/Permissions остават бъдеща архитектурна посока.
    `

Следващата естествена стъпка е да свържем `Students/Details` с реалния Enrollment flow и да реализираме Available Courses → Enroll → Pending → Cancel, след което да тестваме целия процес през UI и базата.
